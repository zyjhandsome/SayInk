# 识别可靠性优化与验证（2026-10-20）

本轮已落实跨输入匹配、会后防链式合并，以及可选的多人发言检测。

本文保留第一轮实现与评测快照；后续局部待确认、重复声音检查及独立标注评测见
[第二轮报告](recognition-optimization-round2-20261020.md)。
默认启用前两项；新检测器有独立开关，默认关闭。真实回放显示它能拦截部分未分开的多人声音，
也会明显增加待确认片段，且仍有混音漏检，因此不把它作为默认准确率升级。

本轮没有更换默认 ASR 模型。两段公开音频回放中，开关检测器前后的转写内容一致。
没有逐字、逐人金标，不报告 CER、DER 或识别准确率提升百分比。

## 已实现的行为

| 场景 | 当前行为 |
|---|---|
| CAM++ 下同人换麦克风/电脑声音来源 | 对所有候选比较，跨来源需要更强相似度和候选差距；弱证据待确认，来源变化不再强制新建编号 |
| 自动跨来源命中 | 不凭这次命中更新声音档案；已保存的人工纠正仍可明确关联来源 |
| 频谱回退 | 保留原有分来源匹配，不以频谱摘要宣称跨来源人物识别 |
| 会后声组 A≈B、B≈C，但 A 与 C 不相似 | 合并前检查两个组里所有原始中心的相互一致性，阻止中间组桥接误并 |
| 检测器发现疑似重叠/未分开的多人 | 保留全部音频供 ASR 使用；说话人待确认，不新建或更新单人档案 |
| 已加载的检测器推理失败 | 本段待确认，不绕过检查训练档案；正常完成文字转写 |
| 可选检测模型加载失败 | 保留可用的 CAM++，界面显示检测加载失败，本场未启用该增强 |
| 会中修改检测设置或下载模型 | 使用已有公共设置的等待规则，本场与待处理音频完成后生效 |

跨来源相似度至少需要 0.80，并满足本场更严格的阈值和原有歧义检查。
这是一条保守规则，尚未按多人多设备金标完成阈值标定，不能理解为身份核验。
人工确认冲突、未知段、容量限制、手动编号和场次隔离继续保留。

会后合并使用完整连接约束，不改写已锁定的不同人工身份。
当前依然不能把已经归进同一编号的不同真人重新拆开；这需要带时间位置的重分配。

## 可选检测器及使用方式

1. 设置 → 引擎：下载「多人发言检测（实验性）」（约 2 MB）。
2. 通用 → 识别 → 高级识别设置：开启「增强说话人区分」与「多人发言检测（实验性）」。
3. 在下一场持续转写或会议使用；运行状态会区分实际加载、加载失败与未加载。

检测开关是 `stt.speaker_activity_enabled`，默认 `false`。
仅下载模型不自动开启，也不加入首次会议的必需辅助模型下载和安装包默认模型清单。
当前源码环境已安装 ONNX Runtime 1.23.2，并验证了本地模型文件；没有改动用户的实际配置开关。
新的安装包尚未打包。

模型来自转换作者的固定版本
[csukuangfj/sherpa-onnx-pyannote-segmentation-3-0](https://huggingface.co/csukuangfj/sherpa-onnx-pyannote-segmentation-3-0/tree/340b52f1f5cd12d45a30fa284691417eaad2ff92)。
模型与 MIT LICENSE 都纳入现有下载器的版本固定和 SHA-256 校验。
新增运行依赖已写入 `requirements.txt`；打包入口显式收集 ONNX Runtime，
本机已有对应 PyInstaller hook，但本轮没有执行完整 EXE 构建。

检测在现有可取消识别线程中执行：CPU 单线程、10 秒窗口、最长 15 秒输入。
根据模型自带的采样率、感受野和帧位移还原有效帧范围，补齐的静音不参与声音计数。
校验固定的 7 类 powerset 输出，分别包含静音、三位局部说话人和三个双人重叠状态。
局部标签不作为本场人物编号，不保存音频或声纹。

当前使用持续至少 200 ms 的重叠概率证据，或两种各持续至少 300 ms 的局部单人状态，
拒绝片段训练。模型和阈值会漏检，也可能过度拒绝；该检查不分离声音、不恢复被覆盖的词，
不提供准确的词级说话人对齐。

## 真人音频诊断

复用此前的公开音频缓存：
[《十三邀》片段](https://www.bilibili.com/video/BV1oy4y1m7yY/)与
[杨澜访谈周星驰片段](https://www.bilibili.com/video/BV1aT4y1K7YX/)。
模型实际加载为 CAM++、Silero VAD、Fun-ASR-Nano，ASR 为 CPU 4 线程、中文、无热词。

以下受控测试使用真人片段的拼接、响度配平和叠加，不能代替自然会议金标：

- 完全相同的 5 秒声音，先以 mic、再以 system 输入：此前现场编号为 **1、2**，现在为 **1、1**。
- A 4 秒 → B 0.8 秒 → A2 4 秒：原有切点仍约为 5.64 秒，没有修复为真实拼接点。
  关闭新检测时两段均可学习；开启后，包含插话的第一段待确认且不训练，末段仍匹配原声组。
  这是减少错误证据写入，不是已经识别出了每个短回应。
- 两个响度配平后单独播放的来源片段对照仍各为一段、可学习，两个来源未被合并。
- 受控等响混音仍有漏检：关闭与开启检测时，都出现了把混音建立为新声组的情况。
  检测到的片段能够阻止训练，未检测到的混音仍可能污染档案，不能宣称重叠问题已解决。

## 108 秒离线应用链路回放

每个来源取前 54 秒，按会议 Silero 规则切段，实际运行 `TranscribeWorker`，
再经过当前 `MeetingSpeakerSession`。先关闭可选检测器，再对同一输入开启。
这不是声卡实时采集；后台线程到 GUI 的交付另由真实 QThread 回归覆盖。

下表来自全部自动化测试结束后的独立复测；先前并发检查时的耗时不用于此表。

| 来源 / 检测 | 归档段数 | 待确认段 | 归属覆盖率 | 处理秒数 | RTF |
|---|---:|---:|---:|---:|---:|
| 长讲 / 关闭（默认） | 4 | 0 | 100.0% | 20.422 | 0.378 |
| 长讲 / 开启 | 4 | 3 | 25.0% | 20.205 | 0.374 |
| 访谈 / 关闭（默认） | 7 | 1 | 85.7% | 23.226 | 0.430 |
| 访谈 / 开启 | 7 | 3 | 57.1% | 23.922 | 0.443 |

覆盖率是已归属片段占比，不是正确率。没有人工金标，不能断言被拒绝的片段全部正确或全部错误。
这个下降足以说明当前检测不能直接默认开启，也不能通过更多待确认来宣称准确率提高。

两段音频在开关前后分别为 230、228 个输出字符，完整转写 SHA-256 分别一致。
所有原分段中的采样点均被保留，检测器不删除或重写语音。
单次 RTF 不代表性能上限；本次各项仍高于项目 0.3 的处理余量目标，
长讲中开启项略快也不能解释为检测器加速了 ASR。

仅包含数值与文本摘要哈希的结果：
[独立复测 JSON](../build/recognition-optimization-replay.json)。
复现脚本为 [recognition_optimization_replay.py](../build/recognition_optimization_replay.py)，
默认读取本机既有系统临时目录中的 `source.wav` / `dialogue.wav`。
原音频与转写正文不写入报告、仓库或应用数据库。
